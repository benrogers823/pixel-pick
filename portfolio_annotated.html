The Crime Landscape: Advanced SQL Analysis

An analysis into three Police forces, comparing differences in rural against urban crime statistics.

Data Source: All crime records were downloaded from the UK Police open data platform at data.police.uk. The site provides monthly CSV exports per police force covering reported crime incidents and associated outcome records.

Force Selection: Three forces were chosen deliberately to create contrast between environments:

  • Metropolitan Police — large urban force covering Greater London; provides high-volume data and dense crime clusters
  • Avon & Somerset — mixed urban/rural force covering Bristol and surrounding countryside; acts as a middle ground for comparison
  • Northern Ireland — predominantly rural force with a distinct socio-political context; the smallest dataset provides the rural baseline

Database Setup: The downloaded CSVs were imported into a single SQLite database. Two tables were created: crimes (containing every reported incident with location, type, force, and LSOA data) and outcomes (containing investigation results linked by Crime ID). SQLite was chosen as a lightweight, file-based RDBMS that requires no server — ideal for a standalone portfolio project.

Data Period: A single monthly snapshot was used for each force to keep the dataset comparable and manageable. A multi-month dataset would introduce seasonality and trend analysis beyond the scope of this project.

Query Writing Approach: All 10 queries were written with a clear analytical question in mind first — the SQL was never written for its own sake. Each query answers a specific investigative question about crime patterns, and the technique chosen (CTE, window function, CASE, HAVING, etc.) was the most appropriate tool for that specific question.

SQL Dialect: All queries are written in SQLite-compatible SQL. Minor syntax differences exist versus PostgreSQL or SQL Server (e.g., SQLite does not support FULL OUTER JOIN natively), but all core analytical functions used here — window functions, CTEs, CASE, HAVING, NULLIF — are ANSI SQL standard and will run unchanged on any major database system.

01
Crime Type Distribution Analysis
WINDOW FUNCTIONS · PARTITION BY · PERCENTAGE CALCULATIONS
Calculates the percentage distribution of each crime type within each police force using window functions to create running totals partitioned by force.
▼
SELECT
    Force,
    "Crime type" as CrimeType,
    COUNT(*) as CrimeCount,
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (PARTITION BY Force), 2) as PercentageOfForce
FROM crimes
WHERE "Crime type" IS NOT NULL
GROUP BY Force, "Crime type"
ORDER BY Force, CrimeCount DESC;

-- Window function SUM() OVER (PARTITION BY Force) calculates total crimes per force
-- This allows percentage calculation without a separate subquery
-- Result: Percentage breakdown showing crime mix varies by force

Why a window function instead of a subquery? The alternative approach would be a correlated subquery or a self-join — both are significantly slower on large datasets. The window function SUM(COUNT(*)) OVER (PARTITION BY Force) computes the total per force in a single pass over the already-grouped data, making it both more efficient and more readable.

The * 100.0 trick: Multiplying by 100.0 (not 100) forces SQLite to perform floating-point division rather than integer division. Without this, 5 / 100 would return 0 rather than 0.05.

Key finding from this query: Violence and ASB together account for over 50% of all crimes across every force — establishing these as the primary focus for the rest of the analysis.

02
Outcome Success Rates by Crime Type
CTE · JOINS · WINDOW FUNCTIONS · STATISTICAL ANALYSIS
Uses a CTE to join crimes with outcomes, then applies window functions to calculate outcome distribution percentages for each crime category, revealing investigation effectiveness patterns.
▼
WITH crime_outcomes AS (
    SELECT
        c."Crime type" as CrimeType,
        o."Outcome type" as Outcome,
        COUNT(*) as OutcomeCount
    FROM crimes c
    LEFT JOIN outcomes o ON c."Crime ID" = o."Crime ID"
    WHERE c."Crime type" IS NOT NULL
    AND o."Outcome type" IS NOT NULL
    GROUP BY c."Crime type", o."Outcome type"
)
SELECT
    CrimeType,
    Outcome,
    OutcomeCount,
    ROUND(OutcomeCount * 100.0 / SUM(OutcomeCount) OVER (PARTITION BY CrimeType), 2) as PercentageOfCrime
FROM crime_outcomes
ORDER BY CrimeType, OutcomeCount DESC;

-- CTE creates reusable dataset of crime-outcome relationships
-- LEFT JOIN ensures all crimes included even without outcomes
-- PARTITION BY CrimeType allows percentage calculation per crime category
-- Key Finding: Drug offences have 3.2x higher charge rates than theft

Why a CTE here? The query requires two logical steps: first aggregate crimes with their outcomes (the CTE), then calculate percentages across those aggregated results. Without a CTE this would require nesting an aggregation inside another query's FROM clause — a derived table — which is harder to read and debug. The CTE separates the two concerns cleanly.

LEFT JOIN vs INNER JOIN: A LEFT JOIN was used to retain all crime records even where no matching outcome exists in the outcomes table. An INNER JOIN would silently discard crimes without outcomes, introducing selection bias into the percentage calculations.

Why this matters analytically: This query establishes the baseline for understanding policing effectiveness — it shows that the type of crime is a stronger predictor of a charge being made than the force investigating it.

03
Geographic Hotspot Identification
GROUP BY · HAVING · AGGREGATION · FILTERING
Aggregates crimes by location and force, filtering for high-activity areas using HAVING clause to identify geographic concentrations requiring intervention.
▼
SELECT
    Force,
    Location,
    Latitude,
    Longitude,
    COUNT(*) as CrimeCount,
    COUNT(DISTINCT "Crime type") as UniqueCrimeTypes
FROM crimes
WHERE Location IS NOT NULL
AND Location != 'No location'
AND Latitude IS NOT NULL
GROUP BY Force, Location, Latitude, Longitude
HAVING CrimeCount >= 5
ORDER BY CrimeCount DESC
LIMIT 100;

-- HAVING clause filters aggregated results (post-GROUP BY)
-- COUNT(DISTINCT) identifies crime diversity at each location
-- Geospatial data (Lat/Long) enables mapping and visualization
-- Result: 100 hotspots account for disproportionate crime volume

HAVING vs WHERE — a common interview question: WHERE filters rows before grouping; HAVING filters after aggregation. You cannot use WHERE CrimeCount >= 5 because CrimeCount doesn't exist as a column until after GROUP BY runs. HAVING is the correct clause for filtering on aggregate results.

Why COUNT(DISTINCT "Crime type")? A location with 10 crimes all of the same type (e.g., car park with 10 vehicle thefts) is a different policing problem to a location with 10 crimes of 8 different types (town centre with mixed crime). The distinct count adds a dimension of crime complexity to the hotspot ranking.

Data quality note: The Location != 'No location' filter was necessary because the Police API anonymises exact locations for some crimes — those records contain the string "No location" rather than a real place name.

04
Violence Crime Pattern Analysis
CASE STATEMENTS · CATEGORIZATION · WINDOW FUNCTIONS
Uses CASE statements to categorize crimes into violence vs non-violence groups, then calculates proportions using window functions to compare force profiles.
▼
SELECT
    Force,
    CASE
        WHEN "Crime type" LIKE '%Violence%' OR "Crime type" LIKE '%sexual%'
        THEN 'Violence/Sexual Offences'
        ELSE 'Non-Violence Crimes'
    END as CrimeCategory,
    COUNT(*) as Count,
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (PARTITION BY Force), 2) as Percentage
FROM crimes
WHERE "Crime type" IS NOT NULL
GROUP BY Force, CrimeCategory
ORDER BY Force, Count DESC;

-- CASE statement with LIKE operator for flexible pattern matching
-- Window function enables percentage within each force
-- Reveals violence accounts for 32.4% of all crimes
-- Proportion varies by force characteristics and geography

Why CASE with LIKE rather than an exact match? The Police API crime type field contains values like "Violence and sexual offences" — using an exact string match would be brittle if the API ever changes the wording slightly. The LIKE '%Violence%' pattern is resilient to minor text variations. Both the Violence and sexual patterns are checked with OR to capture the full Home Office crime category.

Key insight this query revealed: Avon & Somerset has the highest violence proportion (49.1%) despite being a mixed urban/rural force — higher even than the Metropolitan Police (32%). This counter-intuitive finding became one of the headline results of the analysis, prompting the normalisation work in later queries to understand whether this was a genuine pattern or a dataset artefact.

05
Investigation Status Distribution
NESTED CASE · PATTERN MATCHING · AGGREGATION
Employs nested CASE statements with LIKE pattern matching to categorise investigation outcomes, revealing systemic patterns in case resolution across forces.
▼
SELECT
    Force,
    CASE
        WHEN "Last outcome category" LIKE '%investigation%' THEN 'Under Investigation'
        WHEN "Last outcome category" LIKE '%charged%' OR "Last outcome category" LIKE '%court%'
            THEN 'Charged/Court Action'
        WHEN "Last outcome category" LIKE '%no suspect%' THEN 'No Suspect Identified'
        WHEN "Last outcome category" IS NULL THEN 'No Outcome Recorded'
        ELSE 'Other Outcome'
    END as InvestigationStatus,
    COUNT(*) as Count,
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (PARTITION BY Force), 2) as Percentage
FROM crimes
GROUP BY Force, InvestigationStatus
ORDER BY Force, Count DESC;

-- Multiple LIKE conditions capture outcome text variations
-- NULL handling ensures complete data coverage
-- Critical finding: 64.8% of crimes end with no suspect identified
-- Suggests opportunities for investigative process improvement

NULL handling is essential here: The Last outcome category field is NULL for crimes that have never had an outcome recorded. Without the explicit WHEN ... IS NULL THEN 'No Outcome Recorded' branch, these records would fall through to the ELSE bucket and be misclassified as "Other". Explicitly handling NULLs makes the data complete and honest.

CASE evaluation order matters: SQL evaluates CASE branches top-to-bottom and stops at the first match. The most specific conditions (charged, no suspect) are placed before the broad ELSE catch-all to prevent over-classification.

The 64.8% finding: Nearly two thirds of all crimes across all three forces result in no suspect being identified. This is consistent with published Home Office statistics and validates the dataset's integrity — an important cross-check before drawing conclusions.

06
Anti-Social Behaviour Pattern Analysis
FILTERING · AGGREGATION · DATA QUALITY METRICS
Filters for ASB crimes and aggregates by location while calculating data completeness metrics to identify intervention priorities.
▼
SELECT
    Force,
    Location,
    COUNT(*) as ASBCount,
    ROUND(AVG(CASE WHEN Latitude IS NOT NULL THEN 1 ELSE 0 END) * 100, 2) as PercentageWithLocation
FROM crimes
WHERE "Crime type" = 'Anti-social behaviour'
AND Location IS NOT NULL
GROUP BY Force, Location
HAVING ASBCount >= 3
ORDER BY ASBCount DESC
LIMIT 50;

-- WHERE clause filters for specific crime type
-- AVG with CASE calculates data quality metric (geolocation completeness)
-- HAVING filters for statistically significant clusters (3+ incidents)
-- Result: ASB concentrates in public transit and shopping areas

The AVG(CASE WHEN ... THEN 1 ELSE 0 END) pattern is a standard SQL technique for calculating the percentage of rows meeting a condition without a separate subquery. The CASE converts each row to a 1 or 0, and AVG across those binary values gives the proportion directly. Multiplying by 100 gives the percentage. This is a highly reusable pattern for data quality auditing in SQL.

Why focus on ASB separately? Anti-Social Behaviour is notable because it is not a criminal offence in itself — it is a classification that covers a wide range of behaviours. Unlike other crime types, ASB records often carry less precise location data, which is why the geolocation completeness metric was added as a data quality check for this specific category.

07
Drug Offences by Socioeconomic Area (LSOA)
GEOGRAPHIC AGGREGATION · MULTI-LEVEL GROUPING
Aggregates drug crimes by Lower Layer Super Output Area codes to reveal socioeconomic correlations and geographic clustering patterns.
▼
SELECT
    Force,
    "LSOA name" as Area,
    COUNT(*) as DrugOffenceCount,
    COUNT(DISTINCT Location) as UniqueLocations
FROM crimes
WHERE "Crime type" = 'Drugs'
AND "LSOA name" IS NOT NULL
GROUP BY Force, "LSOA name"
HAVING DrugOffenceCount >= 2
ORDER BY DrugOffenceCount DESC
LIMIT 50;

-- LSOA (Lower Layer Super Output Area) enables socioeconomic analysis
-- COUNT(DISTINCT Location) shows geographic spread within area
-- Multi-level grouping (Force + LSOA) for comparative analysis
-- Finding: Strong clustering suggests targeted intervention opportunities

What is an LSOA? Lower Layer Super Output Areas are small geographic units defined by the Office for National Statistics, each containing approximately 1,500 residents. They were designed to have similar population sizes, which makes them valid units for comparing crime rates — unlike comparing a city ward to a village parish. LSOA codes are linked to the Index of Multiple Deprivation, enabling socioeconomic overlays on the crime data.

Why analyse drug offences at LSOA level? Drug offences are one of the few crime types where police enforcement decisions (where to patrol, who to stop and search) heavily influence the recorded crime rate. Clustering at LSOA level can reveal whether drug offence numbers reflect actual drug use or enforcement intensity — a methodologically important distinction for honest analysis.

Theft Crime Subcategory Breakdown
PATTERN MATCHING · WINDOW FUNCTIONS · TREND ANALYSIS
Uses LIKE operator to filter theft-related crimes and window functions to calculate relative proportions, revealing theft patterns across forces.
▼
SELECT
    Force,
    "Crime type" as TheftType,
    COUNT(*) as Count,
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (PARTITION BY Force), 2) as PercentageOfForce
FROM crimes
WHERE "Crime type" LIKE '%theft%'
OR "Crime type" LIKE '%Burglary%'
OR "Crime type" LIKE '%Robbery%'
GROUP BY Force, "Crime type"
ORDER BY Force, Count DESC;

-- Multiple LIKE operators capture theft category variations
-- OR logic creates comprehensive theft filter
-- Window function calculates theft proportion of total force crimes
-- Identifies 5 distinct theft subcategories with unique characteristics

Why combine Theft, Burglary, and Robbery into one query? Legally these are distinct offences (Burglary involves entering a building; Robbery involves force or threat against a person; Theft is property taken without violence). However, analytically they share a common driver — property crime motivated by material gain — and are often discussed together in policing strategy. Grouping them allows comparison of the property crime landscape across forces while preserving the legal subcategory distinctions in the output.

The PARTITION BY Force here calculates each theft subcategory as a percentage of all crimes for that force (not just all theft crimes). This gives a truer picture of how significant theft is to each force's overall workload.

Charge Rate Effectiveness Analysis
CTE · JOINS · CONDITIONAL AGGREGATION · NULLIF
Most complex query: Uses CTE with joined tables, conditional aggregation with SUM(CASE), and NULLIF to prevent division by zero while calculating investigation success metrics.
▼
WITH crime_charges AS (
    SELECT
        c."Crime type" as CrimeType,
        c.Force,
        SUM(CASE WHEN o."Outcome type" LIKE '%charged%' THEN 1 ELSE 0 END) as ChargedCount,
        COUNT(*) as TotalWithOutcome
    FROM crimes c
    LEFT JOIN outcomes o ON c."Crime ID" = o."Crime ID"
    WHERE c."Crime type" IS NOT NULL
    AND o."Outcome type" IS NOT NULL
    GROUP BY c."Crime type", c.Force
)
SELECT
    CrimeType,
    Force,
    ChargedCount,
    TotalWithOutcome,
    ROUND(ChargedCount * 100.0 / NULLIF(TotalWithOutcome, 0), 2) as ChargeRate
FROM crime_charges
WHERE TotalWithOutcome >= 10
ORDER BY ChargeRate DESC;

-- CTE with SUM(CASE) for conditional counting (charges only)
-- NULLIF prevents division by zero errors
-- Statistical significance filter (>= 10 outcomes)
-- Key Finding: Charge rates vary 3.2x between crime types
-- Demonstrates investigative resource allocation effectiveness

This is the most technically demanding query in the project and was designed to showcase several advanced techniques simultaneously.

SUM(CASE WHEN ... THEN 1 ELSE 0 END) is the conditional aggregation pattern — a way to count only rows that meet a condition within a group. It is equivalent to COUNT(*) FILTER (WHERE ...) in PostgreSQL, but the CASE approach is ANSI-standard and portable across all SQL dialects including SQLite.

NULLIF(TotalWithOutcome, 0) returns NULL if the denominator is zero, which causes the division to return NULL rather than throwing a divide-by-zero error. This is defensive programming practice in SQL — important when the data might contain groups with zero matching records.

The TotalWithOutcome >= 10 filter is a statistical significance threshold. A charge rate of 100% for a crime type with 1 outcome is not meaningful. Ten outcomes is the minimum for a rate figure to be worth reporting — a pragmatic threshold for a dataset of this size.

10
Public Order Offences Clustering
MULTI-FIELD GROUPING · STATISTICAL FILTERING
Groups by multiple geographic fields (Force, Location, LSOA) to identify public order incident concentrations with statistical significance filtering.
▼
SELECT
    Force,
    Location,
    "LSOA name" as Area,
    COUNT(*) as PublicOrderCount
FROM crimes
WHERE "Crime type" = 'Public order'
AND Location IS NOT NULL
GROUP BY Force, Location, "LSOA name"
HAVING PublicOrderCount >= 2
ORDER BY PublicOrderCount DESC
LIMIT 50;

-- Three-level geographic grouping (Force > Location > LSOA)
-- Enables both broad and granular geographic analysis
-- HAVING clause ensures statistical relevance
-- Result: Public order crimes concentrate in urban centers and nightlife districts
-- Suggests targeted resource deployment strategies

Why three geographic levels? The data contains both a street-level Location field and an area-level LSOA name field. Grouping by both simultaneously gives two useful things: the exact street cluster (useful for patrol planning) and the broader neighbourhood context (useful for community intervention strategies). Including Force in the GROUP BY ensures results don't accidentally merge locations from different forces that happen to share a street name.

Public order as a lens on nighttime economy: Public order offences are heavily concentrated around licensed premises and town centres on Friday and Saturday nights. Analysing their geographic clustering reveals patterns in how different forces manage nighttime economy crime — a notable contrast between the urban Metropolitan force and rural Northern Ireland.

Visualization Tool: All charts on this page are built with Chart.js v4, a JavaScript charting library that renders to HTML Canvas elements. Chart.js was chosen because it produces interactive, responsive charts that are fully self-contained in the HTML file — no server required to view them. The raw data is embedded directly in the JavaScript arrays from the SQL query results.

Chart type selection rationale:

  • Grouped bar — used for side-by-side force comparisons where absolute counts matter (makes volume differences visible)
  • Doughnut/Pie — used for part-to-whole relationships (outcome distributions, theft subcategories) where proportions are the key message
  • Polar area — used for top crime types overall where the reader needs to quickly identify the dominant category
  • Horizontal stacked bar — used for violence vs non-violence because it makes 100% proportional comparisons across forces easier to read than vertical bars

Colour scheme: Crimson = Metropolitan Police, Gold = Avon & Somerset, Cyan = Northern Ireland. These colours are used consistently across every chart so the reader builds an intuitive association — a deliberate data visualisation design decision.

Why normalise? The three forces contribute vastly different numbers of records to the dataset: Metropolitan Police (93,724 crimes), Avon & Somerset (12,892), Northern Ireland (5,558). If raw counts were compared directly, the Metropolitan Police would dominate every chart simply because of its larger dataset — not because crime is proportionally higher there. Normalising to a per-1,000-records rate removes this size distortion and allows genuine behavioural comparisons between forces.

How the rate was calculated: For each force and crime type, the rate was calculated as:
(CrimeTypeCount / TotalForceCrimes) × 1000
This is equivalent to asking "out of every 1,000 crimes recorded by this force, how many were of this type?" — a standard epidemiological rate approach applied to crime data.

The headline counter-intuitive finding: After normalisation, Avon & Somerset has a higher violence rate (491 per 1,000) than the Metropolitan Police (320 per 1,000). This challenges the assumption that urban environments are more violent. One hypothesis is that rural/suburban forces have fewer of the lower-severity property crimes that dilute the Met's violence proportion — but this warrants further investigation with full population data.

Why focus the detailed breakdown on Metropolitan Police? With 93,724 crime records, the Metropolitan dataset is large enough to produce statistically reliable subcategory breakdowns. Performing the same detailed breakdown for Northern Ireland (5,558 records) would risk over-interpreting patterns that may simply reflect small sample variation. The Metropolitan data provides the most robust foundation for granular analysis.

Drug offence distribution caveat: The sharp skew towards Metropolitan Police in drug offence numbers (2,123 vs 289 for Avon & Somerset vs 178 for Northern Ireland) likely reflects enforcement intensity rather than proportionally higher drug use in London. Stop and search powers are used more frequently by the Metropolitan Police, generating more recorded drug offences. This is an important methodological limitation to acknowledge when presenting the drug data.

ASB data note: Anti-Social Behaviour incidents are recorded differently to criminal offences — they do not require evidence to the same standard, and local authorities as well as the police can record them. The large ASB counts in the Metropolitan dataset partly reflect the higher density of reporting mechanisms available in urban areas.

Tableau enables interactive exploration of the same data — stakeholders can filter, drill down, and discover patterns themselves rather than being shown a fixed chart.
